# InformationBoard Publishing, Access, and QR Design

**Date:** 2026-07-28
**Phase:** 4 of the InformationBoard delivery roadmap
**Status:** Implementation-ready

## 1. Objective

Phase 4 turns a private draft into a shareable board without changing its
stable slug. An owner can publish publicly, require a visitor password, return
the board to private draft mode, control search indexing where allowed, and
download a QR code containing only the canonical board URL.

Attachments remain assigned to Phase 5. Per-board JSON transfer remains
excluded because Supabase is the source of truth.

## 2. Lifecycle and Visibility

`public.boards` remains authoritative:

- lifecycle: `draft` or `published`;
- visibility: `private`, `public`, or `password`;
- `published_at` is set by a database trigger on the first transition to
  `published` and cleared when returning to `draft`;
- the slug is created once and never changes during publication updates;
- `allow_indexing` is valid only for a published public board.

The valid owner operations are:

- keep or return a board to a private draft;
- publish it publicly, optionally allowing indexing;
- publish it with password access and indexing disabled.

Publishing requires a non-empty title and Markdown body. A password must be 8
to 128 Unicode characters after validation, is never returned to the client,
and is never written to application logs.

## 3. Database Read Boundary

Owner reads and mutations continue through the authenticated Supabase client
and existing owner RLS policies.

Anonymous visitors receive direct database access only to rows where
`status = 'published'` and `visibility = 'public'`. The `anon` role receives
column-level `SELECT` privileges for the public presentation fields and cannot
select `owner_id`, lifecycle internals, or any private-schema table.

Password-protected and private rows are never exposed by the anonymous RLS
policy. Password access is resolved on the server after verification and
returns an explicitly projected public-board shape.

## 4. Routes

- `/boards/[id]/edit`: owner publication settings and QR controls.
- `/b/[slug]`: visitor board or password challenge.
- `/b/[slug]/qr.png`: downloadable PNG QR.
- `/b/[slug]/qr.svg`: downloadable SVG QR.

Missing, draft, private, and unauthorized boards use the same generic not-found
response. QR routes exist only for published public or password-protected
boards.

## 5. Publication Mutations

Publication settings use strict schemas and an optimistic `revision`.

The public and private-draft transitions update only the owner row through the
authenticated RLS client. Password publication:

1. validates the owner and input;
2. hashes the password with Argon2id in the Node.js server runtime;
3. stores only the hash in `private.board_secrets`;
4. updates the board to `published/password`;
5. removes or replaces the hash when visibility changes.

The private secret write and board transition use one owner-checked database
function so partial publication cannot leave the row and secret inconsistent.
The function is unavailable to anonymous users.

## 6. Visitor Password Access

Failed attempts use `private.access_attempts` keyed by board ID and an HMAC of a
coarse anonymous request key. Raw IP addresses are never stored.

- five failures inside 15 minutes cause a 15-minute lock;
- a successful check clears the active failure record;
- responses do not reveal whether the board, password hash, or visitor key
  exists;
- attempts use a server-only signing secret with domain-separated HMAC inputs.

Successful verification sets a board-scoped cookie:

- lifetime: 12 hours;
- `HttpOnly`;
- `SameSite=Lax`;
- `Secure` in production;
- path restricted to `/b/[slug]`;
- signed payload containing only board ID and expiry.

Changing or removing the board password invalidates prior access through a
secret-version value included in the signed payload.

## 7. Public Rendering and Metadata

The public board reuses the safe Markdown renderer and controlled theme tokens.
It is mobile-first and never renders raw HTML.

Public, indexable boards emit canonical metadata and allow indexing.
Password-protected, private, draft, and non-indexable boards emit
`noindex, nofollow`. Password responses and challenges are private and
non-cacheable. Published public content may use short revalidation and must
refresh when publication settings change.

## 8. QR Generation

QR payloads are derived from:

`NEXT_PUBLIC_APP_URL + /b/[slug]`

The password is never included. QR images are generated on demand and are not
stored in PostgreSQL or Supabase Storage. Downloads provide deterministic
filenames, correct MIME types, and `nosniff`; SVG output is generated by the QR
library rather than accepting user-authored markup.

## 9. Testing

- pgTAP covers automatic publication timestamps, stable slugs, anonymous public
  reads, denied draft/password/private reads, and denied sensitive columns.
- Unit tests cover publication schemas, state transitions, URL construction,
  password hashing, signed cookies, and lockout calculations.
- Component tests cover publication settings, password validation, public
  rendering, challenge errors, and QR controls.
- Route tests cover generic not-found responses, metadata, cache headers, and
  PNG/SVG response headers.
- E2E covers public publication, stable URL updates, password unlock and
  lockout, private withdrawal, and QR downloads.

## 10. Exit Gate

Phase 4 is complete when:

- changing a published board preserves its slug and QR address;
- anonymous database access returns only published public fields;
- private and password-protected content cannot be fetched before authorization;
- five failed password attempts lock access for 15 minutes;
- a successful access cookie expires after 12 hours and is board-scoped;
- QR codes contain the canonical board URL without a password;
- lint, typecheck, unit tests, E2E, build, database tests, dependency audit, and
  secret scan pass.
